# Desktop Local Gateway Discovery Contract

> Status: Proposed
> Created: 2026-05-01

## Purpose

Define a future contract for how the CrewCmd desktop shell may discover local
OpenClaw gateway candidates and hand them to the CrewCmd server for validation
and ownership.

This document is intentionally docs-only. It does not add desktop code, package
dependencies, runtime bundling, install flow, or public CLI behavior.

## Context

The first desktop shell runs in server URL mode and does not bundle, launch, or
supervise OpenClaw. Local gateway discovery is still useful because many users
will run CrewCmd in a desktop window while their OpenClaw gateway is already
running on the same machine.

Discovery must help the server connect to an existing gateway without making
the shell responsible for runtime control, secrets, authorization, or
orchestration.

## Contract Principles

- Discovery finds local candidates; it does not prove trust by itself.
- The CrewCmd server validates, imports, stores, and owns gateway records.
- The desktop shell must not bundle or start OpenClaw for this flow.
- Candidate payloads must be minimal and non-sensitive by default.
- Logs and diagnostics must describe discovery outcomes without leaking tokens,
  prompts, file paths beyond the necessary endpoint source, or raw gateway
  responses.
- Failure should be explicit, retryable where possible, and safe to ignore.

## Candidate Sources

The desktop shell may scan only local, user-scoped, low-risk sources.

Allowed sources:

- loopback HTTP endpoints on known gateway ports
- user-approved server URL entry, including `http://localhost` and
  `http://127.0.0.1`
- documented OpenClaw user config locations, if the user has opted in or the
  file is explicitly part of a desktop settings import flow
- environment variables visible to the desktop process only when the user
  chooses diagnostic discovery

Disallowed sources:

- arbitrary local network ranges
- non-loopback private network scanning
- privileged system directories
- shell history
- SSH config, cloud credentials, or provider key stores
- reading arbitrary workspace files
- browser profiles, cookies, or password stores

The first implementation should prefer a short deterministic candidate list
over broad scanning.

## Candidate Shape

Discovery should produce a candidate object with enough data for server-side
validation, but not enough to create trust without validation.

```ts
type LocalGatewayCandidate = {
  id: string;
  endpoint: string;
  source: "known_port" | "manual_url" | "user_config" | "diagnostic_env";
  discoveredAt: string;
  platform: "darwin" | "linux" | "win32";
  confidence: "low" | "medium" | "high";
};
```

Rules:

- `endpoint` must be loopback unless the user manually entered a different
  server-approved URL.
- `id` must be generated by CrewCmd and must not include secrets or local file
  paths.
- `source` must be coarse enough for diagnostics without exposing private local
  structure.
- The candidate must not include bearer tokens, API keys, process arguments,
  raw config file contents, or gateway response bodies.

## Validation Flow

Discovery validation is server-owned.

Expected flow:

1. The shell gathers local candidates.
2. The shell sends candidates to the configured CrewCmd server through an
   authenticated session.
3. The server validates the candidate endpoint using its gateway connection
   contract.
4. The server asks the user for any required token or approval in the existing
   CrewCmd UI.
5. The server imports or updates the gateway record.
6. The shell displays only server-provided status.

The shell may perform lightweight reachability checks to avoid presenting dead
endpoints, but those checks are not authorization and must not mutate gateway
state.

Server validation must check:

- endpoint scheme and loopback constraints
- gateway health endpoint shape
- gateway version compatibility
- required auth challenge or token flow
- team, company, and user permission to import the gateway
- duplicate gateway records for the same endpoint

## No Runtime Bundling

Local gateway discovery must not install, bundle, launch, upgrade, supervise, or
terminate OpenClaw.

Out of scope:

- embedding OpenClaw binaries in the desktop shell
- starting gateway processes during shell launch
- changing gateway config files
- upgrading a local gateway
- creating desktop-only runtime state
- managing gateway logs or workspaces from native code

If CrewCmd later adds a bundled local runtime mode, that mode needs a separate
ADR because it changes data ownership, update semantics, crash recovery,
storage locations, and support expectations.

## Server-Owned Import

Gateway import is a server workflow, not a native desktop workflow.

The server owns:

- gateway records
- credential collection and storage
- authorization checks
- duplicate detection
- audit events
- runtime status shown in the product UI
- reconnect and retry policy
- gateway removal or disconnect semantics

The shell owns only:

- local candidate discovery
- sending candidates to the configured server
- showing server-provided status or errors
- clearing local transient discovery state

The shell must not write directly to CrewCmd database tables, runtime config,
or OpenClaw config during import.

## Privacy And Logging

Discovery logging must be privacy-preserving by default.

Allowed logs:

- number of candidates found
- candidate source type
- sanitized endpoint host category, such as `localhost` or `loopback`
- validation outcome code returned by the server
- retryable or non-retryable failure status

Disallowed logs:

- tokens, passwords, API keys, or auth headers
- full gateway response bodies
- raw config file contents
- shell environment dumps
- prompt, chat, tool, or agent workspace data
- unredacted local file paths unless the user explicitly exports diagnostics

Diagnostics should prefer structured reason codes over free-form native error
messages. Any user-exported diagnostic bundle must redact endpoints and paths
unless the user opts into including them.

## Failure Modes

Discovery failures must not block normal desktop shell use.

Expected failure codes:

```ts
type GatewayDiscoveryFailureCode =
  | "discovery_unavailable"
  | "permission_denied"
  | "candidate_unreachable"
  | "invalid_endpoint"
  | "unsupported_gateway_version"
  | "auth_required"
  | "server_validation_failed"
  | "duplicate_gateway"
  | "server_unavailable"
  | "native_error";
```

Rules:

- `discovery_unavailable`, `permission_denied`, and `native_error` are shell
  failures.
- `invalid_endpoint`, `unsupported_gateway_version`, `auth_required`,
  `server_validation_failed`, and `duplicate_gateway` are server validation
  outcomes.
- `server_unavailable` should leave candidates in transient local memory only;
  the user can retry after reconnecting.
- A failed candidate must not be imported optimistically.
- A failed scan must not clear existing server-owned gateway records.

## User Experience Requirements

The UI should present discovery as an optional assistive path, not as the only
way to connect a gateway.

Requirements:

- Manual gateway URL entry remains available.
- The user can dismiss discovered candidates.
- Candidate labels must avoid implying trust before validation.
- Validation errors should point to the server-owned connection flow.
- Retry should rescan candidates instead of replaying stale privileged data.

## Verification For First Implementation

Before implementing this contract, add focused verification that confirms:

- discovery scans only approved candidate sources
- non-loopback automatic candidates are rejected
- candidate payloads do not include secrets or raw config contents
- server validation owns import decisions
- failure codes are structured and non-sensitive
- desktop shell use continues when discovery fails

## Open Questions

- Final list of known OpenClaw gateway ports.
- Whether user config discovery should be opt-in per scan or a persistent
  setting.
- Exact server API route for candidate validation.
- Whether diagnostics should hash loopback ports for privacy or show them
  directly.
- How duplicate gateway records should be presented across multiple companies.
